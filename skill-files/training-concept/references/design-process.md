# 共通生成指示：研修設計の進め方

> このファイルは HR Monster（https://nkitou-alt.github.io/hr_monster/）が公開する研修スキル群の共通参照資料です。自組織に合わせて自由に書きかえて使ってください。


このファイルは、LLMが研修を設計・開発する際の「進め方の手順」を定義する。  
「良い研修とは何か（前提・価値観）」は共通コンテキスト資産（context）に、  
その研修に固有の情報は個別層の context.md に書かれている。本ファイルは  
それらを「どう使って設計を進めるか」を示す。

## 読み込み順序と優先ルール

1. まず common/context.md（共通の前提）を読む。
2. 次に当該研修の context.md（個別の前提）を読む。
3. 個別に overrides があれば読む。
4. 矛盾する場合は各ファイルのフロントマター precedence に従い、値の強い  
    ものを優先する（base < override < override-strong）。
5. 原則どうしが競合する場合は、context 第1章の優先順位に従う  
    （このスキルの初期設定では「対話からの創発」を最上位に置く）。

## 全体を貫く4つの姿勢

- **勝手に決めず、要所で問い返す。** 設計を左右する分岐点では、思い込みで  
    進めず、選択肢を示して設計者に判断を仰ぐ。ただし context / 個別 context に  
    既に答えがある事項は問い返さない（重複確認は手戻りを増やす）。
- **時間で必ず殴り返す。** どんな良い設計案も、器（実働時間）に収まらなければ  
    絵に描いた餅。案を出したら必ず分単位で積み、器に収まるか検証する。
- **背骨を通す。** その研修の最重視の到達点と context の最上位原則を、全ての  
    セッションが体現しているかを常に確認する。途中で背骨からズレたら戻す。
- **確定前に、自己批評する。** 主要成果物（構成表・教材一式など）を提出する  
    際は、自ら「プロとしてさらにブラッシュアップする観点」を挙げ、設計者の  
    採否を仰いでから確定する。求められるまで待たない。設計者の承認は品質の  
    上限ではなく下限であり、その上に載せられる改善は提出側から出す。

## ファイル運用ルール（全フェーズ共通）

- **バージョン管理**：成果物は「資産名_v◯.◯」で命名し、フロントマター  
    （layer / type / title / version / updated / owner / depends / precedence）を  
    必ず持つ。更新時は旧版を残し、新番号で保存する。
- **波及チェック**：あるファイルを変更したら、フロントマターの depends を  
    手がかりに、それに依存する下流ファイルを洗い出す。即時更新するか、  
    「未反映」として申し送りに明記するか、どちらかを必ず行う。黙って放置  
    しない（例：宿題文言の変更 → 案内文・動画台本・当日スライドへの波及）。
- **資産台帳の維持**：プロジェクトごとに、全成果物の状態（確定／仮・要  
    磨き込み／未着手）を一覧する台帳を1枚維持し、作業の区切りごとに更新する。  
    会話・セッションをまたいで再開する際は、この台帳の確認から始める。  
    LLMは会話をまたぐと文脈を失うため、台帳が再開時の共通の足場になる。
- **プレースホルダ規約**：未確定事項（日付・会場・URL・氏名など）は  
    【 】で統一表記し、各ファイルの末尾または申し送りに未確定リストを持つ。  
    確定時は【 】を全ファイル横断で検索して差し込む。
- **正文の同期**：複数媒体に現れる依頼文・定義文は、context 第4章の正文  
    管理に従う。制作時は正文からコピーし、改変しない。レビュー時に媒体間の  
    文言一致を確認する。

## フェーズ0：0次設計（学習構造・メインワーク・大まかな時間配分）

目的：研修全体の骨組みと、価値の中心（メインワーク）を定める。

### 手順

1. 個別 context.md から「最重視の到達点」を確認する。これが設計の中心。
2. その到達点を最も直接に生む活動を「メインワーク」として特定する。  
    ここに最も多くの時間を割く前提で全体を組む。
3. 高度なワークには足場かけ(カード・フレーム等)を前提に時間を積む。
4. 全体の流れ（例：発散→収束）を一本の線として描く。各セッションが  
    その線のどこに位置するかを説明できる状態にする。
5. 大まかな時間配分（ブロック単位）を置く。この時点では分単位でなくてよい。  
    各セッション末のリフレクション枠（context 第5章）もこの時点で見込む。
6. 反転学習を採る場合、**情報開示マップ**を定める（context 第3章）。  
    何を事前教材で開き、何を当日の体験・サプライズに温存するかを明記する。

### 問い返すべき分岐点（例）

- 研修の日程・拘束時間の形（連続／非連続、1日の長さ）。
- 1クラスの人数規模（グループ編成・演習の成立可否に直結）。
- 最重視の到達点が個別 context に無い、または複数あって優先が不明なとき。
- 複数の原則が競合し、その研修特有の事情で優先を上書きすべきか判断が要るとき  
    （例：知識の確実な習得が最優先の研修では、創発最上位を上書きしてよいか）。
- 宿題・持ち込み素材のスコープ（対象とする相手・場面の範囲。入口の広さが  
    参加のしやすさと素材の質を左右する）。

### 完了の目安

実施イメージが立つ骨格になっている。メインワークと全体の流れが定まっている。

## フェーズ1：1次設計（最小コンテンツ化と実現可能性チェック）

目的：0次の骨格が、所定時間内に無理なく回るかを検証する。教材の作り込みは  
まだしない。

### 手順

1. 最も負荷が高く、崩れると研修が成立しないブロック（多くはメインワーク）  
    から着手する。
2. そのブロックを、1人あたり・1ラウンドあたりの分数まで分解する。
3. 「単位時間 × 人数（グループ人数）」で総時間を積む。これを研修の器  
    （実働時間）と突き合わせる。
4. 収まらなければ、削る／人数を絞る／構成を変える、の選択肢を出す。  
    価値の高い対話・深掘り・承認の時間を優先的に守り、情報伝達側を削る。
5. context 第5章の時間ルールを適用する（同種ワークを連続させない、90分ごとに  
    小休憩、午後は対話で立ち上げる、レクチャーは長くて15分、長い個人ワークの  
    合間に「動」を挟む、各セッション末のリフレクション枠）。
6. 人数の端数（奇数グループ等）の吸収ルールを決める。
7. 進行が押した場合の**削り順**（スキップ・短縮の優先順位）と、余った場合の  
    延ばし先を決めておく。メインワークは最後まで削らない側に置く。
8. 実現可能性の懸念点を、2次設計への申し送りとして明記する。

### 問い返すべき分岐点（例）

- グループ人数を何名で固定するか（総時間と質のトレードオフが生じるとき）。
- 当日の講師・ファシリテーターの人数（足場かけを人で吸収するか設計で吸収するか）。
- サーベイ等の外部インプットの形式（数値のみ／記述付き等。解釈の足場かけの  
    厚みが変わる）。
- 学びの現場への着地点（研修内で完結か、1on1・職場共有につなげるか。  
    クロージングの重さが変わる）。
- リフレクション枠の配置方針（毎セッション末か、要所のみか。最終セッション  
    と重複する場合の統合可否）。

### 完了の目安

両日／全ブロックが器に収まることを分単位で確認済み。無理のある箇所は  
申し送りとして言語化されている。

## フェーズ2：2次設計（実施用の作り込み）

目的：1次設計の骨格を、研修テキスト・動画・当日スライド・事前学習・  
ワークシート・受講者アンケート・（必要なら）研修中に使うLLMプロンプトとして実施用に仕上げる。

### 手順

1. 1次設計の申し送り事項を先に解消する（時間の詰め、動の要素の配置など）。
2. **物理フォーマットを冒頭で確定する。** スライドテンプレート・配布物の  
    判型・デザイン語彙（色・フォント・レイアウトの型）を最初に共有・確定し、  
    「サンプルは準拠必須か、変更可の参考か」を設計者に確認する。フォーマットが  
    後から届くと、生成の基盤ごと作り直しになる。
3. **大物成果物は二段階で作る。** 分量の大きい成果物（目安：スライド50枚超、  
    長尺の文書・台本）は、いきなり本制作せず「構成表（一覧）→ 設計者の承認 →  
    本制作」の順で進める。構成段階の修正は安く、本制作後の修正は高い。
4. context 第4章の教材要素（扉→狙い→進行→内容→まとめ→リフレクション等）に  
    沿って各セッションを具体化する。
5. 測定整合（context 第8章）を実装する。リフレクション記入項目・アンケート  
    到達度設問・事後フォローを、学習目標と同じ語彙で作る。
6. context 第7章のトーン、第8章の品質基準、第9章のNGパターンに照らして  
    自己点検する。特に「対話が雑談に劣化しないための条件（良い問い・安全な場・  
    足場かけ・対話のゴール設定）」が各対話ワークに備わっているかを確認する。
7. 研修中にLLMを使うワークがある場合、その用途のプロンプトを設計する  
    （個別層 instructions として保存）。出力を「答え」でなく「吟味の叩き台」  
    として位置づけ、吟味の時間を設計に組み込む（context 第6章）。
8. 現場への転移を設計する。学びを誰と・どの場で・どう共有するかまで含める  
    （用途別の持ち帰り成果物、声に出す練習など）。

### 問い返すべき分岐点（例）

- セクション扉・章名のスタイル（テーマ名か、セッション名か、併記か）。
- アンケートの匿名／記名（率直さと事後フォローとの紐付けのトレードオフ）。
- 事後フォロー（実施後サーベイ等）の有無とタイミング。
- 講師デモの相手役など、当日運営の未確定要素をどの案で置くか。

### 完了の目安

そのまま実施できる教材一式が揃い、品質基準・NGパターンの自己点検を通過して  
いる。資産台帳上の「仮」項目が、意図した残タスクだけになっている。

## 既存資産の改訂プロトコル（v1.2追加）

完成済みの大型資産（テキスト・プレイブック等）に、設計進化を反映する  
ときの手順。いきなり本文を書き換えない。

1. **差分の棚卸し（改訂要件書）**：設計側で確定した変更を一覧化し、  
    それぞれの由来（どの設計資産の何章か）を明記する。
2. **先決事項の特定**：改訂の可否を左右する前提（例：配布タイミング、  
    正文の親子関係）を洗い出し、選択肢を利点・難点つきで提示して先に  
    確定させる。原本を読むと、設計側の想定と原本の前提が食い違っている  
    ことがある（例：当日配布のつもりが、原本は事前読み物として書かれて  
    いた）。**食い違いは要件書段階で表面化させる。**
3. **改訂骨子（章別対応表）**：原本の章構成×差分の対応表を作り、承認を  
    得る。既存の骨格は壊さず「増補＋同期」で成立させる方針を基本とする。
4. **差分本文の執筆**：変更・新設部分は完全本文、保存部分は【原文のまま】  
    マーカーで明示する。原本の文体（文の長さ・語り口）に合わせて書く。  
    保存すべき白眉（原本の最良の文章）は指定して守る。
5. **同期チェックリスト**：改訂完了後に確認すべき他資産への波及  
    （案内文言・スライドの整合など）を原稿末尾に添付する。

## 印刷物・図版・配布物の派生生成（v1.2追加・技術ノート）

スライド資産から本・配布物用の派生物を作るときの実務知見。

- **図版の単体化**：テキスト（本）へ挿入する図は、スライドからタイトル・  
    パンくず・フッターを外した図版単体として再生成し、高解像度PNG  
    （2500px幅以上）＋余白トリミングで納品する。挿入作業側（Google  
    Slides等）にはPNGが最も安全。
- **テンプレート装飾の除去**：会社テンプレートのロゴ・フッターは  
    スライドレイアウト／マスター側に居る。テキストはsp要素だが、**ロゴは  
    画像（p:pic）のことがある**ため、除去はpicとsp の両方を対象にする。
- **A4縦の配布物**：presentation.xmlのsldSzを A4縦（cx=7560000,  
    cy=10692000）に変更すれば、スライド生成の道具立てのままワークシートを  
    組める。記入欄は白地＋薄グレー罫のボックスで統一。
- **add_slideの罠**：複製スクリプトはsldIdLstの末尾に自動でエントリを  
    追加する。挿入位置を指定する場合は、自動追加分を除去してから目的位置に  
    挿入すること（怠ると同一スライドが2回現れる）。
- **文言の機械同期**：ワークシート等の設問文言は、正文の所在（スライド  
    XMLのa:t）から機械抽出して転記する。手打ちの写経は表記ズレの温床。
- **表記の機械適用**：箇条書き句点などの表記ルールは、スライドXMLを  
    一括走査して適用する（疑問文の「？」は除外）。目視での統一は漏れる。

## ワークシートの設問設計（v1.3追加）

ワークシートは、ちょっとした言い回しがワークの質を左右する繊細な資産。  
設問は「情報を集める枠」ではなく「受講者の内的プロセスを起こす装置」  
として設計する。以下は、設問を書く／レビューするときの原則。

### 語彙は「その時点で導入済みのもの」だけを使う

- 設問に、まだ研修で導入していない概念語（例：「クセ」「べき」）を  
    先取りで使わない。未習語での内省要求は飛躍を生み、受講者のペンが  
    止まる。設問の語彙は、そのワークまでに受講者が獲得した言葉で書く。
- 到達点の語（設計者が使う概念）と、その時点で受講者が持っている語は  
    別物。リフレクション設問は特に後者で書く。

### 「効果の先取り」をさせない

- まだ体験していない変化を予測させる設問（例：「〜すると、どんな良い  
    変化が生まれそうですか」）は、優等生的な回答を誘発し、体験を浅くする。
- 予測ではなく、行動の選択肢を開く問いにする（例：「ほんの少し緩めると  
    したら、どんな関わりができそうですか」）。効果は約束させず、余地を残す。

### 誘導を「禁止」するのではなく「扱える形」にする

- 実務者（マネジャー等）が内心に持つ意図（「相手をこう変えたい」）は、  
    消せと言っても消えない自然なもの。設問で意図を否定・禁止しようとすると、  
    かえって不自然になる。
- 意図を書き出させた上で、「持っていていい。ただし、いったん脇に置く」と  
    いう扱い方を注記する。意図の自覚と留保を促すほうが、禁止より深い学びに  
    なる（該当研修の核心と一致させる）。

### ロール別シートは、役割ごとに設問の視点を厳密に分ける

- 複数の役割（例：聴き手／話し手／観察者）が使うシートは、見出しと設問  
    内容の視点を役割に厳密に一致させる。観察者シートに主観評価の設問が  
    混じる、といった視点の混線は、ワークの意味を壊す。
- 「事実の再生」を求めるシートには、評価語（良い・悪い・上手）を使わせ  
    ない注記を添える。

### 表記・体裁のレビュー観点（配布物として）

- 設問番号は記入順（上から①②③）と一致させる。番号の乱れは記入者を迷わす。
- 用語・言い回しは、スライド・テキスト等の他資産と統一する（正文同期）。  
    例：メンバー像の表現が資産間でぶれると、受講者の受け取りがぶれる。
- 相手を評価・非難する含意の語を避ける（例：「動いてくれない」より  
    「思うように動かない」。前者は主語がこちらの期待に寄り、相手を責める  
    響きが出る）。
- 記入欄は、その問いに求める分量に見合う高さを与える（一言で足りる問いと、  
    深く書く問いで、欄の大きさを変える）。句点重複などの誤植を最終目視する。

### レビューのしかた

- 設問を「設計者の意図」ではなく「受講者がその場で読んだときにどう動くか」  
    で読み直す。重要度順に、①ワークの成否に直結する構造（役割の混線・  
    未習語・誘導の要請）→②コーチング等の原理レベル→③トーンの一貫性、で  
    点検する。

## 実施後：フィードバックの還元

- 実施で得た知見のうち、その研修に固有のもの（つまずき事例、良い／悪い成果物の  
    実例）は個別 context.md に追記する。
- 複数の研修に共通して効く一般則に昇格できるものだけを common に上げる。  
    判断基準は「3つ目の研修でもそのまま使えるか」。7割の研修で使わないものは  
    common に入れない（共通層は小さく保つ）。
